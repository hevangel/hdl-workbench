HDL Workbench · overview

SystemVerilog, simulated in your browser

HDL Workbench pairs a Monaco editor with the Xezim simulator compiled to WebAssembly and the Surfer waveform viewer, all in one browser tab. A local AI agent can drive the same tab over MCP.

One rule shapes everything: simulation always runs as Xezim WebAssembly inside a browser Web Worker. Nothing falls back to a native, server-side or JavaScript simulator. If the WASM assets are missing, the Run button stays disabled.

Life of a run

The same path serves the Run button and an agent's run_simulation call. Pick a step to highlight it in the diagram above, or play the whole sequence.

1 · Edit

In browser-only mode you edit in Monaco, and saves go to the browser's origin-private file system with a revision check. When an agent is paired, the disk folder becomes the authority. The agent calls write_project_file with the revision it last read, and a stale revision returns REVISION_CONFLICT instead of overwriting your work.

2 · Snapshot

Before every run the bridge hashes the project into a snapshotId and synchronizes those exact bytes to the browser workspace. The controller recomputes the snapshot from file revisions and refuses to run a mismatched one. Logs and waveforms keep that ID, so every result traces back to the sources that produced it.

3 · Compile DPI helpers

Project .c/.cpp files are compiled by a pinned Clang/LLD toolchain running as WebAssembly in its own Worker. Each becomes a standalone, import-free .wasm module. The browser ABI is narrow: int functions with scalar input int arguments, and extern "C" for C++. A compile error returns DPI_COMPILATION_FAILED.

4 · Simulate

The Xezim Worker receives the snapshot, top module, stop time and limits, then compiles and simulates in one bounded call. $readmemh, $fopen and $display work against project-relative virtual files. A wall-time guard terminates the Worker after at most 300 s, and allocation past the 256 MiB WASM ceiling reports RESOURCE_LIMIT.

5 · Store the waveform

The VCD is written into a bounded in-memory sink (up to 64 MiB) and persisted in OPFS as a waveform artifact with its run ID, snapshot ID and timescale. Waveform bytes never travel through MCP JSON; only artifact metadata does.

6 · View

Surfer runs as WebAssembly in a same-origin iframe and receives the artifact as an object URL. Only the versioned SurferAdapter knows Surfer's unstable internal messages, which it uses to load, add signals, set the cursor and zoom. An agent can call show_waveforms to open the run you're both looking at.

7 · Report

The run result carries a status (completed, finish, failed, timeout or resource_limit), stdout/stderr, structured diagnostics with file and line, the last simulated time and the waveform reference. The IDE shows it in its panels and marks diagnostics in the editor. The agent receives the same result over the bridge.

Two ways to work

Both modes use the same browser simulator. The bridge only changes where files live and who is allowed to request runs.

BROWSER ONLY

Just open the IDE

Static files only: the IDE shell, Xezim WASM and Surfer. Projects live in your browser's origin-private storage and survive restarts.

  • Edit, set Top module, press Run.
  • Export or import projects as ZIP files to move between profiles.
  • No bridge, network service or account needed.
AGENT CONNECTED

Pair a local AI agent

The agent runs the MCP bridge against a folder on disk and pairs with your open tab. You watch every edit, run and waveform happen.

  • Tools: list_project_files, read_project_file, write_project_file, run_simulation, get_simulation_log, get_diagnostics, list_runs, show_waveforms.
  • Disk is the source of truth while paired, so browser-side ZIP import and file actions are locked.
  • Close or disconnect at any time from Connect agent.

Agent pairing and trust

The bridge can read and write your project, so a connection requires an explicit act in your own browser.

  1. bridgeStarts with an explicit --project-root and listens on 127.0.0.1 only (default port 47531). It has no implicit workspace.
  2. agentCalls get_connection_status and receives the WebSocket URL and a single-use pairing code that expires in two minutes.
  3. youClick Connect agent, paste the JSON, and press Pair browser.
  4. bridgeAccepts only an exact allow-listed Origin and a valid code. It then issues a session token, checks it on every message, and expires it after one hour. One browser session at a time.
  5. workerEvery run_simulation executes in your tab's Xezim Worker. The bridge forwards files and requests; it never runs commands or a simulator.

Limits

These are deliberate, tested boundaries of the first release. Exceeding them returns a named error instead of a hang or a silent truncation.

10,000,000 ns
maximum stop time, in whole nanoseconds
300 s
wall time per run, enforced by terminating the Worker
256 MiB
WebAssembly linear memory per simulator Worker
4,096 files · 16 MiB
project input to the browser simulator
64 MiB
per VCD; 8 VCDs and 128 MiB retained
1 MiB → 16 MiB
captured output, default and maximum
Not supported in the browser: native DPI/VPI .so/.dll plugins, DPI tasks and non-int DPI arguments, Python/cocotb, full UVM, FST output, multithreaded or JIT simulation, and pause, resume or in-run cancellation. The MCP compile tool reports UNSUPPORTED_CAPABILITY, because the browser binding compiles and runs in one step.
